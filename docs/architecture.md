# Architecture

## Product direction

Relay is a native, task-centered agent workspace. A named project owns a server root and independent repository, board, and directory connections. Work can start on a local task board, then be published to GitHub/GitLab while preserving task and session identity. Connected remote boards remain authoritative. Conversations, delegation, verification, and results preserve provenance.

Agent profiles configure harness, execution, scope, responsibilities, completion, permissions, worker limits, and the worker model policy. Director and Worker are presets, not separate agent implementations. The Director preset permits delegation; the Worker preset denies it by default. Project-scoped named profiles can be saved and reused. Instance changes do not mutate the saved preset. A session's worker limit covers only its own descendants. Child sessions can select their own profile, but the configuration's limit and every ancestor's limit still cap their subtrees.

Generated context gives standing guidance to act on responsibilities within the user's task and effective permissions. Responsibilities identify areas of focus; completion is an evidence and outcome checklist, not an ordered pipeline or permission grant. Missing Implement responsibility does not prohibit permitted implementation. With Delegate Allow, agents should use Relay MCP delegation when useful without requiring a fresh delegation request each turn; when Delegate is also a responsibility, agents act as directors: they delegate every change to repository files to a worker and verify the results. Directors work directly only for read-only investigation, answering questions, planning, verifying or reviewing worker results, and trivial edits of a few lines they have already located; a change that looks small is not a reason to implement it directly, and uncertain size means delegate. Directors stay available to the user: they do not call `wait_for_agents` or otherwise block a turn to await workers, but report status and end the turn after spawning or messaging workers, then review results when workers report back or the user asks. Relay starts a director turn when a worker reports a result. A director that is itself a worker (it has a parent) still calls `report_result` to that parent once it has accepted its workers' results, in the turn Relay starts when they report back rather than by blocking; ending a turn while its workers run is not a report. After accepting a worker's result as done, directors archive that worker with `archive_agent`; rejected results, workers that need follow-up, and active workers are not archived. Without a Delegate responsibility, trivial work or work better done directly need not be delegated. Delegate Ask still requires human approval and Deny forbids spawning regardless of responsibilities or completion. Allow does not authorize unrelated external or destructive work. Higher-priority instructions, user restrictions, wider-child-permission approval, Relay-only spawning, workspace isolation, worker limits, and the explicit merge/push/deploy/remote-board restrictions remain in force.

Directors coordinate workers, follow work to its configured completion criteria, and surface decisions that need human attention. A project may have multiple specialized directors. The workflow is opt-out; direct interaction with agents remains part of the product. Declarative profiles guide behavior and supported action boundaries will be enforced outside the agent's prose instructions.

Execution belongs on the server. Clients can disconnect, reconnect, and share sessions from different machines. The interface treats conversations as interactive documents, with keyboard navigation and contextual review. Efficiency controls remain explicit: compact and continue, reset context while retaining history, and archive/start a linked session. Cache and usage claims must distinguish measured state from estimates.

## Foundation boundaries

`relay-core` defines the domain, profile resolution/validation, fixture seed, and protocol. `relay-server` owns storage, authorization, mutations, and event publication. `relay-ui` is the Mosaic component library of the orchestrator design: tokens and themes, fonts, primitives and composites (agent tree, transcript, tool calls, composer, usage, surfaces) that take plain view models and callbacks and never depend on `relay-core`. `relay-desktop` contains the interface and a background network runtime: `Model` owns state and commands, `src/adapt/` maps the snapshot into `relay-ui` view models with pure, unit-tested functions, and the views compose `relay-ui` components without restyling them: sections share their parent's rules, and a missing prop, slot or label is added to the `relay-ui` component generically rather than rebuilt in the desktop. Reactive UI objects never cross worker threads; Mosaic's state channel delivers network updates to the UI thread.

The demo board and transcripts are immutable fixtures. Named projects coexist in the sidebar; changing the selected project or board does not stop agents elsewhere. Boards own their columns and task memberships, separately from stable task identities. Local tasks have no fabricated provider reference. A source issue can belong to several boards within one project. Explicit synchronization retains the last confirmed board on failure and preserves removed tasks for history; work requires active membership. GitHub imports issue items across all repositories, excluding draft issues and pull requests. GitLab supports project/group Open/Closed and label lists; unsupported filters/list types produce explicit errors rather than a misleading mirror.

Repositories clone under `ROOT/repos/HOST/NAMESPACE/REPO` using the server's existing Git credentials. `ROOT/workspace` is the default directly writable directory. Each new repository session receives isolated worktrees beneath `ROOT/.relay/sessions/SESSION`, with a recorded base and review per repository. Connected ordinary directories are edited directly under the execution policy. Sessions capture their resource IDs at launch; later connections never silently widen a resumed thread's writable roots. Existing sessions retain their original paths and exact harness thread. `UpdateConnection` changes only a connection's display name, with the same transactional receipts as other commands; it cannot change paths, remotes, resource IDs or captured session roots. The name already exists in the stored snapshot, so this command needs no schema migration.

By default each worktree builds into its own `target/`, which Relay reclaims when the session is archived. A shared Cargo build directory per project is opt-in: with `RELAY_SHARED_BUILD_CACHE` set to `1`, `true`, `on`, or `yes`, Relay sets `CARGO_TARGET_DIR=ROOT/.relay/cache/cargo-target` unless the server environment already sets `CARGO_TARGET_DIR`, and adds the directory to the Codex writable roots and the Claude sandbox `allowWrite` list. It is off by default because workspace crates keep the same names in every worktree: concurrent workers building the same crate in different worktrees overwrite each other's test binaries, so one worker's `cargo test` can run another worktree's code. Remove the cache directory to reclaim it; Relay does not prune it. A compiler cache such as `sccache` (`RUSTC_WRAPPER=sccache` in the server environment) shares compiled dependencies safely while keeping per-worktree target directories; Relay does not configure one.

Agent sessions always reference a local task or remote issue and a root configuration. A root agent’s first conversation creates a local planning task, or binds a selected task from its configured scope. Root session names retain the configured agent name. Each turn checks current scope, effective action permission, board membership, and worker limit; Ask requires approval and Deny prevents that turn. Root sessions do not consume subagent slots. Codex uses app-server stdio; Claude Code uses streaming JSON/control protocol. Both report transcript, thread identity, lifecycle and measured usage. Completed means the turn ended, not independently accepted work. Agent completion never commits, integrates, publishes a board, or changes remote status automatically.

The project picker shows project names, agent counts, and aggregate running-worker state; individual agents appear only in the selected project tree. Unstarted root configurations appear there as idle agents and open their first conversation; their definition is replaced by the session row after launch. The child action is disabled until the parent has started. The Agents header + opens New Director, and a row’s hover/focus + opens New Worker with that row as its parent. New Agent uses a profile selector in its title. Modified defaults can be applied to this instance, saved as a named project profile, or discarded.

Human `StartChildAgent` commands create children of active or completed agents, fork the parent’s current workspaces, capture the selected profile, and launch a first task. They require a connected trusted client, preserve parent/task/project provenance, and recheck scope, implementation approval, board membership, and the root worker budget. The command receipt makes retries idempotent. Human configuration is independent of the parent’s permission to delegate autonomously.

Any session can create child sessions through Relay MCP when its effective Delegate permission permits it. Children retain the parent's project, director and linked task, have role Worker, and can delegate at any depth. Repository workspaces fork the parent's current staged, unstaged and untracked state; connected ordinary directories remain shared within the tree. Worker limits are per subtree. An active (queued or running) child occupies one slot of its parent and of every further ancestor; each ancestor allows at most its own `max_workers`, capped by the agent configuration's limit. A session's own turns are checked only against its ancestors' slots, so a director whose children fill its own slots can still respond and review results. Root sessions occupy no slot. Workers started directly from the board have no parent and share their configuration's limit among themselves; their descendants use the worker's own slots, not that pool. Spawns and resumed turns beyond a limit are rejected until a slot frees. Scope and board membership are checked again at process launch. Permissions inherit along parent links, then apply each child SpawnGrant's overrides. Delegate Ask and any widening in the Deny < Ask < Allow order require explicit human ToolPermission approval on the caller before spawning. Implementation Ask also requires approval for the child's first turn. The child's effective map is enforced on subsequent queue submissions and process launches. Merge and Deploy remain workflow intent rather than separate harness tool enforcement.

`stop_agent` requests termination of the caller’s own descendants and their subtrees, pauses their queues, and revokes their run capabilities. It always stops the target's whole subtree, like `StopWorker` with `include_descendants: true`. Delegate Deny rejects it; Ask requires human approval. It retains conversations, results, and workspaces. Parents and unrelated sessions cannot be stopped through this tool.

`archive_agent` archives an inactive descendant and its subtree using `SetSessionArchived`, retaining history and workspaces and pausing queued turns. Delegate Deny rejects it; Ask requires human approval. Self, ancestors, unrelated trees, cross-project links, and queued or running workers anywhere in the affected subtree are rejected. Idle and finished sessions (including stopped, failed, and interrupted workers) can be archived; repeat calls are safe. Director guidance archives workers by default once their results are reviewed and accepted.

`message_agent` queues a normal durable turn for a parent, child or sibling in the same tree, preserving the human's shared draft. Turns sent by `message_agent` and the first turn of a `spawn_agent` child record the calling session as their sender on both the submission and its prompt message; human turns record the user. Clients label an agent-sent prompt with its sender's relationship and title (for example "Parent · Planning"), link the label to that session, and show "Agent" when the sender has been deleted. Relay notice prompts keep the Relay label. Its Message detail becomes read when the target harness consumes the submission. `wait_for_agents` watches snapshots until the specified agents are Completed, Failed, Stopped or Interrupted, or at most 600 seconds elapse; it blocks the caller's turn, so directors should not use it to await workers. `report_result` persists the child's summary, optional attachment path references and worktree path in its transcript and appends an agent_result message with Result detail to the parent's transcript. It does not read attachments, merge changes or accept work. When a child turn ends Completed, Failed, Stopped or Interrupted without calling `report_result` and without another queued turn starting, Relay queues one durable notice turn for its parent (`relay-notice-` submission, prompt authored by Relay) listing each child's title and id, final status, error, worktree and changed-file count. When the parent is a director (Delegate is Allow and a responsibility), a child turn that did call `report_result` also notifies it, with the reported summary, because directors do not block on their workers; other parents await reports with `wait_for_agents` and are not notified of them. A child that ends while its own descendants are still queued or running is not reported as ended: its notice is held until its subtree is idle. When a descendant's end wakes that child (a notice or reported result for it), the child's new turn supersedes the held notice; otherwise, once the last descendant ends, the parent is told the child ended and that its workers have since ended. Notices to a session that has its own parent also remind it to call `report_result` to that parent once its delegated work is accepted. Notice turns have no client receipt; the launch authorizes them from their durable Relay submission without implementation approval. Endings within about two seconds share one notice. Relay skips notices for root sessions, archived parents and runs stopped by an ancestor (the descendants of an `include_descendants` stop, or the target of `stop_agent` and its descendants), since that ancestor already knows; such a stop also drops held notices of the stopped descendants and of the `stop_agent` target. A plain stop of a session's own turn still notifies its parent. A parent with a paused queue receives the notice held, and an idle parent starts it immediately. Pending batches and held notices live in memory, so a restart drops them, and restart repair does not notify. `list_agents` returns the caller's subtree and its parent with current statuses and reported results. `StopWorker` stops only the session's active turn and pauses that session's own queued turns, so a manual stop does not immediately launch the next one; descendants keep running and their queues are untouched. A plain stop is rejected when the session itself has no active turn. `StopWorker` with `include_descendants: true` (the client's "Stop all" session action, shown when any descendant is queued or running) also stops every descendant and pauses their queues, even when the parent itself has finished. Restart repair classifies unfinished descendants Interrupted without replay. Pending permissions remain on their original sessions; metadata retains them across the whole tree so clients can project approvals upward and answer each request once.

Explicit task edits and moves on a remote board go through its provider. Publishing a local board selects a new or existing destination, destination repositories, and column mappings. Each write persists an in-flight journal key before contacting the provider and its result before the next step. Provider APIs do not guarantee exactly-once creation: uncertain outcomes require a validated remote result before continuing. A board becomes remote only after publication and authoritative readback succeed. Publication redirects duplicate board/task identities to the preserved local IDs; historical records, sessions, scopes and receipts retain their original IDs. Session transcripts are retained locally, not exported as issue comments.

Reconciliation commands accept only the exact unresolved journal step. Board and issue results must decode to scoped provider references; membership results require a nonempty item ID; status and edit results require the literal `confirmed`. Steps must belong to the operation's task and kind. Pending markers, column mappings and known results cannot be overwritten. Rejected input leaves the operation unchanged and schedules no continuation.

Execution settings inherit project → director → worker and are captured when each turn launches. Workers retain their original harness across profile changes. Automatic configures Codex workspace-write/never approval or Claude native auto/required sandbox. Ask uses native permission callbacks, recorded with exact run identity and answered inline once. Pending requests expire on terminal state/restart; receipts make answers idempotent. Unrestricted Access explicitly selects native full access/bypass. Server-enforced scope, board membership, action permission, and worker limits apply in every mode. Other profile responsibilities and completion criteria remain workflow configuration; Relay does not yet turn every configured action into a separately enforceable harness tool permission. Session command catalogs discover models, skills, and supported command metadata through bounded, read-only harness subprocesses. Native compaction, retained clear/resume history, and native thread forks use the existing authorization and execution lifecycle. Model, effort, fast tier, and planning selections belong to the session and survive reconnects. Forks copy repository worktrees and preserve staged, unstaged, and untracked changes; connected ordinary directories remain shared. Predictive cache warnings require a later integration. Cached token counts are measurements from completed turns, not a cache-expiry estimate.

One server process owns one SQLite database. Its schema is versioned with `PRAGMA user_version`; schema versions newer than the server are rejected. Schema 23 stores each project's Nix command setting (`nix_commands`, omitted from the snapshot while Off); missing settings load as Off, and the version bump keeps older servers, which would silently drop the setting, from opening the database. It adds no client-visible change that needs a new protocol version: older clients ignore the field, and older servers reject `SetNixCommands`. Schema 22 stores the selection rationale on spawn grants (`SpawnGrant::selection_rationale`, omitted while absent); older grants load without one, and the version bump keeps older servers, which would silently drop the rationale, from opening the database. Schema 21 stores each profile's worker model policy and moves the stored snapshot to protocol 14; missing policies load as the default, and older servers, whose profiles reject unknown fields, refuse the database instead of failing to read it. Schema 20 adds persisted prompt senders to messages and submissions and moves the stored snapshot to protocol 13; older records load every sender as the user, and the version bump keeps older servers from dropping agent senders. Schema 19 adds no stored data; it moves the stored snapshot to protocol 12 so older servers, which ignore `include_descendants` and cascade every stop, reject the database instead of stopping descendants on a single-turn stop. Schema 13 stores reusable agent templates and per-session profiles, normalizes legacy director configuration fields into generic agent configuration fields, and moves snapshots to protocol 6 while preserving sessions, receipts, permissions, and data. Serde aliases exist only to read persisted field names during this migration; Rust APIs use the generic names. Schema 12 rewrites the stored snapshot for protocol 5: sub-agent links, compactions, tool timing and details, usage windows and the usage ledger default to empty, and legacy tool categories are normalized (issue #29). Schema 9 adds persisted tool-call inputs, categories, and lifecycle outcomes (issue #21), with optional metadata for older transcripts. Schema 8 retains the latest measured usage while subsequent turns are queued. Cache retention and future re-cache size remain unknown. Schema 7 adds persisted harness-reported model and context metadata (issue #19), defaulting missing fields in older snapshots to unavailable. Schema 6 adds browser authentication tables. Schema 5 migrates schema 4 and earlier workspaces into project connections and separate board memberships, preserving project/task/director/session IDs, receipts, comments, drafts, assets and exact harness thread/worktree identities. Existing checkouts are neither moved nor cloned again. New servers reject newer schema versions. It updates only unchanged bundled implementation Ask defaults to Allow; custom defaults and explicit overrides remain intact. Shared drafts, draft receipts, immutable assets, and durable submissions remain preserved. Every mutation and receipt is committed in one transaction before publishing the snapshot. Run one server per database; horizontal scaling is not supported.

On shutdown, the server closes WebSocket handlers and terminates owned worker groups. On Linux, process identity includes boot/start information and harness children receive a parent-death signal; restart classifies unfinished runs as Interrupted without relaunching them. When a systemd user manager is available, each harness runs in its own memory-limited transient scope bound to the server unit; an OOM kill then stays inside one worker, and a harness killed by SIGKILL fails its turn as out of memory (see [worker memory](development.md#worker-memory)). Processes that deliberately escape supervision are outside this guarantee. Non-Linux crash cleanup and native behavior still require platform validation. GitHub and Git subprocess captures have output limits and deadlines; transcript messages and review diffs explicitly report truncation.

## Protocol

Workspace routes require `Authorization: Bearer <token>`, including WebSocket upgrade. The shared token defines a trusted workspace, not individual accounts or project roles. Legacy command bodies are bounded to 64 KiB, structured conversation/draft envelopes to 512 KiB, and individual asset uploads to 20 MiB.

`relay-server mcp` runs a newline-delimited JSON-RPC 2.0 MCP server on stdio with initialize (protocol 2024-11-05 and tools capability), notifications/initialized, ping, tools/list and tools/call. Its exact tool names are spawn_agent, stop_agent, archive_agent, message_agent, wait_for_agents, report_result and list_agents, plus run_nix when the agent may run [Nix commands](#nix-commands). tools/list reads the run's policy-specific list from `POST /v1/agent-tools/tools`. Tool calls use `POST /v1/agent-tools/{tool}` using a fresh random per-run capability, bound to session and run. The server stores only its SHA-256 hash in memory and uses constant-time comparison; it rejects the workspace token on this endpoint. These routes use capability authentication instead of workspace browser/protocol middleware. Capabilities expire when execution ends, stops, is superseded or the server restarts. Each mutation rechecks the active run. The server URL and scoped capability pass through RELAY_AGENT_URL and RELAY_AGENT_CAPABILITY in the harness environment; workspace RELAY_TOKEN variables stay stripped. No capability is persisted in snapshots, MCP arguments or config files.

Claude Code receives an inline --mcp-config with environment placeholders and allows only Relay's MCP tool family without extra harness prompts. Codex app-server receives dotted -c overrides for command, args, env_vars and default_tools_approval_mode="approve"; Relay itself enforces all tool policy and human widening approval. See the [official Codex MCP configuration](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) and [Claude environment expansion](https://code.claude.com/docs/en/mcp#environment-variable-expansion-in-mcpjson). The serving process sets the reachable HTTP callback endpoint with Shutdown::set_agent_endpoint after binding its listener. The relay-server binary does this automatically, including ephemeral ports, and launches its own executable with the mcp subcommand. The execution contract uses protocol 6 and schema 13: grants, results and delivery receipts use the existing session, transcript and submission contracts.

| Endpoint | Behavior |
| --- | --- |
| `POST /v1/agent-tools/{tool}` | Agent-tree tools authenticated by a scoped run capability |
| `GET /v1/workspace` | Workspace metadata without archived transcripts or review diffs |
| `GET /v1/ping` | Authenticated empty response; no history or caching |
| `GET /v1/sessions/{session}/history` | Bounded recent, before, after, or around-ID page |
| `GET /v1/sessions/{session}/messages/{message}` | Complete source content on demand |
| `GET /v1/sessions/{session}/search` | Bounded matches and snippets across unloaded history |
| `GET /v1/snapshot` | Complete authoritative snapshot for diagnostics; clients use workspace projections |
| `POST /v1/commands` | Typed command envelope; returns request ID and committed revision |
| `POST /v1/boards/discover` | Read destination metadata and named columns before publication |
| `POST /v1/boards/resolve` | Resolve a pasted GitLab/GitHub board address to existing boards, read only |
| `POST /v1/operations/reconcile` | Validate a known remote result URL and preview recovery without writing |
| `GET /v1/harnesses` | Cached, bounded executable/version/authentication probes on the server |
| `POST /v1/harnesses/refresh` | Refresh read-only harness probes |
| `GET /v1/sessions/{session}/catalog` | Cached server-owned command, model, skill, and MCP metadata |
| `POST /v1/sessions/{session}/catalog` | Refresh metadata without starting a model turn |
| `GET /v1/events` | WebSocket: metadata reset, selected conversation subscription, and revisioned incremental updates |
| `POST /v1/conversation/commands` | Structured turn/queue commands; returns request ID and committed revision |
| `GET /v1/drafts` | Shared draft documents with independent per-session revisions |
| `POST /v1/drafts/{session}` | Compare-and-swap draft save, with an immutable request receipt |
| `GET /v1/drafts/events` | WebSocket: full draft state, independent of transcript streaming |
| `POST /v1/assets/{uuid}` | Immutable binary upload and validated metadata acknowledgement |
| `GET /v1/assets/{uuid}` | Authenticated inline file/image content |

Command envelopes carry `request_id` (UUID), `expected_revision`, and a tagged command. Supported commands register GitHub project/checkout bindings, configure harness executables and execution modes, answer native tool requests, update profiles/comments, synchronize saved projects, and start/send/stop workers. Stale revisions return HTTP 409. Invalid references/configuration return 422; invalid credentials return 401. Unexpected storage failures return a sanitized 500 response. Reusing an ID for a different command is rejected. Execution and provider commands are server runtime operations, not pure domain mutations; durable command receipts prevent duplicate launch on deliberate retry.

Event delivery uses a watch channel: intermediate revisions may coalesce. Each connection diffs its projected state against the last delivered state. Updates identify base and resulting revisions, key records by stable ID, preserve collection order, and send suffixes for appended text. Clients apply updates atomically and reconnect on revision gaps. Reconnection restores workspace metadata and the selected conversation’s recent page, retaining drafts and uncertain request IDs. Writes are not retried automatically; exact receipt retries remain idempotent. A command acknowledgement clears only its submitted draft version, independently of stream delivery; revision-dependent actions and automatic queue promotion wait while state catches up. Stream control metadata includes active-run IDs even when the corresponding prompts are outside loaded history. See [issue #26](https://github.com/jens-hj/relay/issues/26).

Conversation pages contain at most 50 messages within a 256 KiB budget. Oversized messages and comment collections use explicit preview references; full source is fetched on demand before quoting. Scrolling near the top loads earlier messages and preserves the visible reading position. Search jumps load a bounded surrounding page; scrolling to its bottom loads newer history. Review diffs are requested when opening Changes. Browser round trip uses an independent empty HTTP probe, while native clients use bounded WebSocket ping/pong.

The session header's tool-call strip counts the whole conversation, not the loaded page. Stream control metadata (`HistoryState.tool_counts`) carries the selected session's calls per tool category, derived by the server from the complete stored transcript each time it projects an update or history page, in first-seen order. Older transcripts' untyped command and file-change messages count as the categories the transcript shows them as, and a spawn receipt duplicated by an observed spawn counts once, so existing sessions need no backfill. Counts arrive in the same update as the tool message that changes them; the client takes the larger of the server and loaded-page count per category, so a loaded call is never counted twice, and falls back to the loaded page while history for a newly selected session is still arriving. The field is optional and derived, so it adds no persisted state, schema migration or protocol version change.

Legacy comments retain their message IDs and optional quotes. Buffer replies carry a message ID, exact UTF-8 byte range, and source quote, so repeated passages remain distinguishable. Recorded source text is immutable; typing there creates a reply in the shared next-message draft. Every inline and bottom-draft view edits the same ordered parts. Text, assets, and anchored replies survive serialization without flattening their positions.

Draft saves compare their own revision, so token streaming cannot invalidate a save. Submitting compares the saved draft revision and exact content, atomically clears that draft, and creates one durable submission. Exact receipt retries never create another turn. Queue edits retain submission identity and atomically consume a reviewed shared draft. Other queue actions compare the workspace revision; promotion also requires the exact observed active run ID. The desktop retains the original envelope for ambiguous outcomes.

A running agent finishes before queued turns launch, unless the user promotes a specific queued message. Promotion requests `turn/interrupt`, stops the owned process, and resumes the same thread with the promoted payload. Current issue membership, effective permissions, scope, harness, and capacity are checked again at launch. Failure, manual stop, shutdown, or restart pauses unsent work. Restart marks launching/running submissions Interrupted and never replays them; only unsent queued submissions can be explicitly resumed. A crash after delivery cannot guarantee a terminal outcome, and is never treated as permission to replay. `PauseQueue` holds a session's queued turns on request: they become Paused, nothing launches after the current turn while any turn is held, and `ResumeQueue` releases them — launching the next one when the agent is idle, or returning them to the queue behind a running turn. A promoted turn still replaces the running one. Pause reuses the existing Paused state, so it adds no persisted data and needs no schema change; a server that predates the command rejects it without changing the workspace.

Asset metadata must match an acknowledged upload. Drafts are limited to 64 KiB of text/quotes, 1024 parts, and 64 MiB of referenced files; images are validated and limited to 32 megapixels. On each turn the server materializes assets in a private temporary directory outside Git, removes it after the turn, and sends ordered text/localImage Codex inputs or text/base64-image Claude content blocks. Other files are referenced at their exact position and require the agent to use a read tool. Replies identify quoted source explicitly as context. Local recovery stores unsent drafts and pending asset bytes next to client settings with owner-only permissions on Unix. It does not automatically submit recovered work.

## Profiles

Project defaults are complete typed profiles. Directors hold optional overrides. Omitted values follow current project defaults; explicitly set values replace the whole field. Changing defaults validates all affected directors. New directors inherit the current defaults. A reusable complete TOML template can seed a new database via `RELAY_DEFAULT_PROFILE`.

Profiles configure Codex or Claude Code, whole-project or selected-issue scope, responsibilities, completion requirements, a worker limit from 0 to 64, deny/ask/allow permissions for each named action, and the worker model policy described below. Completion requirements are a checklist, not a fixed terminal stage or ordered pipeline. Editing/importing changes a draft; saving validates and persists it. The UI displays effective values and their origins. Harness status distinguishes installation/authentication from model access and managed execution policy. Project bindings are persisted on the server and validate the checkout’s GitHub origin; both current and previously registered boards remain usable.

### Worker model policy

A profile's `worker_models` field (Worker Model in the editor) controls which harness, model and effort the agent's `spawn_agent` workers use (issue #155). It is enforced by the server, not by agent memory, and inherits and overrides like other profile fields.

- **Fixed** (`mode = "fixed"`, `harness`, `model`, optional `effort`): every worker uses exactly these values. `spawn_agent` fills omitted harness, model and effort from the policy and rejects a call that passes a different value, with an error naming the fixed choice. Rejection was chosen over silently overriding so that the agent learns the policy. Without an effort, workers run at the model's default and spawn calls may not choose one.
- **Delegator Chooses** (`mode = "delegator_chooses"`): the delegator picks per worker. An optional `allowed_models` list of `{harness, model}` entries may span connected harnesses; an empty list allows any model of any connected harness. An optional `max_effort` caps effort using the ordering in `relay_core::EFFORT_LEVELS` (none < minimal < low < medium < high < xhigh < max < ultra). Every `spawn_agent` call must pass `harness`, `model` and `effort` explicitly; nothing falls back to the delegator's own profile model. Effort may be omitted only when the harness's catalog lists the model with no effort setting; such a model is not restricted by the cap. When no catalog of the requested harness is cached and the model is allowed, `spawn_agent` first discovers the harness's catalog in the project root, as the profile editor does, before approvals, forks or the child session exist; stopping the run cancels discovery, and a discovery failure rejects the spawn. Fixed policies do not discover. The call must also pass a non-blank `rationale` of at most 1000 characters explaining why the choice fits the task and, when enabled, the capability it needs and remaining usage. Relay stores the trimmed rationale on the child's spawn grant (`SpawnGrant::selection_rationale`, schema 22) and shows it as "model choice" in the expanded spawn call. Relay checks only that a rationale is present, not what it says. Violations are rejected with an error that names the missing values and lists the allowed models and efforts. Two independent considerations guide choice without limiting it: `model_capability` (match model strength and effort to task difficulty) and `available_usage` (prefer harnesses and models with more remaining usage quota).

The default is Delegator Chooses with no allowlist, no effort cap, Model Capability on and Available Usage off. Available Usage starts off because rate-limit windows are per harness rather than per model, are absent until a harness reports them, and preferring quota over capability is a quality trade-off the user should opt into.

Spawned children inherit their parent's effective policy unchanged. A human-created child (`StartChildAgent`) with an explicit profile may only narrow its parent's policy: under a fixed parent it must keep the same fixed choice; under a listing parent its own allowlist must be a non-empty subset and its cap must not exceed the parent's. The child's own model choice remains a human decision, as with human configuration of permissions.

Relay states the effective policy in the director guidance next to the delegation text: the mode, allowed models per harness, maximum effort, the enabled considerations and what each means. Under Delegator Chooses the guidance also asks the director to consider which allowed alternatives suit each task, to pick the best fit even if several workers use the same model rather than vary models for their own sake, and not to assume model rankings it cannot support. With Available Usage on, the guidance also lists remaining usage per harness: the percent left in each current 5-hour and weekly window, from the same usage windows as the usage panel, plus tokens per model from the last week of the usage ledger. `list_agents` returns the policy, a one-line summary and, with Available Usage on, the same usage lines. The MCP bridge asks the server for this run's tool list, so the `spawn_agent` description and schema restrict `harness`, `model` and `effort` to the allowed values; if the server cannot be reached it falls back to the unrestricted schema, and enforcement still happens on the server.

### Nix commands

Harness sandboxes block the Nix daemon socket, so agents cannot build, test or render screenshots through `nix develop` themselves. A project can let its agents ask the server to do it instead, through the Relay MCP tool `run_nix`. The server runs `nix develop WORKSPACE[#SHELL] --command COMMAND…` outside the agent's sandbox, with the server user's access. The command can execute any code in the workspace's flake, so this is execution authority, not a sandbox: neither the `nix` prefix nor the working directory limits what it can do.

- **Owner opt-in.** The project's Nix Commands setting (`Project.nix_commands`, on the Connections page) is Off by default. Only workspace clients can change it, with `SetNixCommands`; agents cannot, and fixture projects reject it. Ask approves each command; Allow runs commands without asking.
- **Permissions.** An agent's effective permission is the strictest of the project setting and its profile's Verify and Implement permissions, because a command can also change files. Allow therefore needs all three; Ask in any of them sends each command to the existing native tool approval, showing the exact command line and directory, and Deny or Off rejects the call before anything runs. `tools/list` includes `run_nix` and the turn guidance describes it only when the effective permission is not Deny. Approval descriptions are limited to 16 KiB, so a command whose complete description would be longer is refused in every mode rather than shown in part. After the command is built, the policy, the active run, the workspace and the one-command slot are checked again, the transcript record is saved and the process is spawned under the single store lock that stops, shutdown and policy changes also take, so none of them can land between the final checks and the launch.
- **Workspaces.** `workspace` must resolve to one of the session's assigned workspaces (the first by default). `directory` and `artifacts` are relative paths inside it: absolute paths and `..` are rejected, and paths that resolve outside the workspace through symlinks are rejected or reported unavailable. `shell` is a development shell name of letters, digits, `-` and `_`.
- **Environment.** The command inherits only a fixed list of server variables (`PATH`, `HOME`, locale, `TMPDIR`, XDG and user-bus variables for the worker scope, Nix certificate and remote settings, `CARGO_TARGET_DIR`, `RUSTC_WRAPPER` and `SCCACHE_DIR`), plus the shared Cargo target when it is enabled. Relay tokens, run capabilities and other variables are not passed. The command can still read the server user's files.
- **Process lifecycle.** Each session runs one command at a time. The command runs in its own process group with the parent-death signal, lowered priority and, when available, the [worker memory](development.md#worker-memory) scope. It is killed with its group when it times out (`timeout_s`, at most and by default 600 seconds), when the agent's run is stopped or the server shuts down, or when the tool call is dropped; the drop path kills the whole group on every Unix platform, without relying on Linux process identity. Relay signals the group only while its leader is unreaped: it observes the leader's exit without reaping it, polling `waitid` with `WNOWAIT` and `WNOHANG` every 20 ms so no call waits and nothing outlives the tool call, kills every process left in the group, and only then reaps the leader, so the kill cannot reach a reused group ID.
- **Output and artifacts.** stdout and stderr are combined. The result carries the exit code or signal, whether it timed out, the duration, the total output size, and its first 8 KiB and last 24 KiB, with the omitted byte count between them. `artifacts` lists files the command should produce; the result returns their resolved paths and sizes, for the agent to pass to `report_result` as attachments, and names any that are missing. Relay does not upload or copy them.
- **Review.** Before launch, the server saves a Relay-authored `mcp__relay__run_nix` tool record, marked Running, with the command line and directory. When the command ends, the server updates that record in place with the outcome, exit code, duration and the same bounded output, even if the run has ended meanwhile; this path changes only that record and adds no other messages. A call dropped mid-run marks it Interrupted after the group is killed. If the outcome cannot be saved, the call returns an error that gives the outcome and says the record was not saved, instead of a normal result; Relay keeps retrying the save in the background for about half a minute and logs the record ID if it gives up. The harness also shows its own record of the tool call, so the tool-call strip counts each command twice.

## Protocol compatibility

Snapshots and stream resets declare `protocol_version: 14`. Every workspace-client mutation requires `X-Relay-Protocol: 14`; older clients receive `protocol_mismatch` before changing state. Agent-tool callbacks use the separate scoped capability endpoint described above. Update server and desktop together. New commands cover project creation, connection management, board/task changes, publication, recovery and task-linked session launch. `POST /v1/boards/discover` reads provider destination metadata for named column choices. `POST /v1/boards/resolve` takes a pasted board address and returns the existing boards it means. The server parses it strictly (https only; no user name, password, port, encoded or relative path parts; GitLab nested groups and projects, self-hosted hosts, and GitHub org/user projects; the fragment and view-state query parameters are dropped, while a GitLab `id` query parameter selects the board like the path number and is refused if it is not a positive number or disagrees with the path). An address that names a board is checked with one read and returns that board. A GitLab group or project address without a board number lists that scope's boards with the server's own `glab` login: one board is returned alone, several are for the user to pick by name, none is an error, and a group address is never read as a project. Only GET requests are made, so it never creates a board. The additive endpoint needs no protocol or schema bump; older servers answer 404 and the client says so. Remote credentials stay on the server; the desktop supplies project and provider identifiers only.

Harness commands and transport contracts use protocol version 6 and database schema 13. Schema 11 updated the stored snapshot protocol version. Migration retains existing transcripts, drafts, receipts, profiles, and workspaces. Skills are durable multipart references with server-validated native identities; clients cannot choose executable skill paths or arbitrary RPC methods. Catalogs expire after 30 seconds and are invalidated by native skill changes. Execution revalidates selected capabilities before starting a turn. Terminal-only commands remain visible with an explanation rather than becoming model prompts.

### Harness data (protocol 5)

Protocol 5 (issue #29) adds data for sub-agents, usage windows, compactions and tool categories. Every field is optional or defaults to empty, and is set only from harness reports:

- `Session.parent_session_id` and `Session.spawn` describe a sub-agent and the grant its parent requested. They are reserved for Relay MCP spawning and are not set yet. Pure helpers in `relay-core/src/tree.rs` walk the tree (children, ancestors, descendants, depth, subtree status counts, subtree pending permissions) and stop at missing parents and cycles.
- `Session.compactions` records every compaction across runs. Codex appends one per completed `contextCompaction` item with the latest context occupancy. Claude Code appends one per `compact_boundary` event using `compact_metadata.pre_tokens`, and adds a "Compaction completed" message for each.
- `ToolKind` is `read`, `edit`, `create`, `search`, `run`, `test`, `fetch`, `plan`, `spawn`, `message`, `wait`, `result` or `other`; stored `terminal`, `web` and `agent` load as `run`, `fetch` and `spawn`. `mcp__relay__spawn_agent`, `message_agent`, `wait_for_agents` and `report_result` map to `spawn`, `message`, `wait` and `result`. Shell commands that invoke a known test runner are `test`.
- `ToolCall.started_ms`/`finished_ms` are the server's observation times. `ToolCall.detail` holds measured facts with lists capped at 200 entries:
  - Codex: line counts for added files (`create`), per-hunk +/− for unified diffs (`edit`), steps from `turn/plan/updated` (`plan`), exit code and `durationMs` for commands (`run`), and pass/fail counts parsed from common runner summaries (`test`; absent when no summary is recognized).
  - Claude Code: `Write` becomes `create` when the result reports a new file; `Edit`/`MultiEdit` +/− from the replaced strings or the reported `structuredPatch`; `Read` line range (total lines only when the structured result reports it); `Glob` matched files; `Grep` hits per file in `count` mode, or in `content` mode when the structured result lists the files; `TodoWrite` steps; `WebFetch` HTTP status; `Bash` test summaries. Claude does not report command exit codes or durations, so `run` has no detail.
  - No harness reports a fetched page title, so `Fetch.title` stays empty. Spawn, Message, Wait and Result details are reserved for Relay MCP spawning.
- `Snapshot.usage_limits` holds the latest five-hour and weekly window per harness (`id` is `{harness}-{window}`). Codex sends sparse `account/rateLimits/updated` notifications without a thread ID; Relay merges the default `codex` bucket's `primary`/`secondary` windows and classifies them by `windowDurationMins`. A window without a reported length is ignored. Relay does not call `account/rateLimits/read`, so no Codex window is shown until Codex sends an update during a run. Claude Code sends `rate_limit_event` with `unifiedWindows` (`five_hour`, `seven_day`) as utilization fractions; it omits them for API-key, Bedrock and Vertex sessions.
- `Snapshot.usage_ledger` gains one entry per finished run with measured usage (the run's harness, model and tokens) and keeps 8 days of entries, pruned on insert.
- Claude Code context occupancy comes from the latest top-level assistant message's input plus cache tokens; the context window comes from the result's `modelUsage` for the reported model, and is left unset when the model is ambiguous.

Chats retain an `archived` flag independently of their linked task and workspace. The server rejects archive requests for running or launching workers and pauses queued turns when a chat is archived. Archived chats retain their transcripts, drafts, harness threads, and captured workspaces, but cannot execute turns or spawn children until unarchived. Unarchiving does not automatically resume paused turns. The sidebar hides archived chats by default; Show archived reveals dimmed, readable rows. Archive and Unarchive are available in Session actions. Protocol 9 and database schema 17 preserve the archive flag and prevent older servers from dropping it.

Agent creation requires neither a name nor a task. Root agents open their prelaunch chat; child agents capture their parent's workspaces and open an idle chat without launching a harness. A persisted `awaiting_first_message` flag allows their first shared-draft submission to launch a new thread through the ordinary permission checks. Blank names enable automatic naming from the first message (normalized whitespace, up to 80 characters); explicit custom names remain fixed. Existing agents retain their names during migration. Protocol 9 and schema 16 preserve both naming mode and the waiting state. Agents created through agent tools continue to launch with their assigned tasks.

Agent profiles carry an explicit model alongside the harness, with the same inheritance and override rules as other profile fields. Changing harness clears an inherited incompatible model. New agents require a model; the configuration picker discovers choices from the selected harness before a session exists and excludes unresolved Default entries. Legacy profiles deserialize without a model but must select one before creating a new agent. Protocol 11 and schema 18 preserve profile models. Before a root chat starts, per-chat model and effort overrides are saved on the agent configuration; without an override, the profile model is copied into the first session. Child sessions inherit an explicit model too. The composer uses the selected model for both identity and effort; the last reported model is only a fallback when no selection is set. The draft is the final editable section of the transcript, with one shared scroll viewport and a full-width divider. Send and attachment controls sit to the right of the draft, with the model ledger on its left. Wide layouts reserve a fixed control gutter outside the transcript reading column, aligning the draft with message bodies even when the ledger folds; narrow layouts place the ledger above the draft while keeping Send and Attach on the right. Draft height is uncapped.

Archive and Unarchive apply to the selected session and all descendants. Archive is unavailable while any worker in the branch is running or queued. Archived tree rows offer Delete; the first click expands the action to Confirm Deletion and the second permanently removes the branch. Protocol 10 and schema 17 support branch deletion, remove transcripts, comments, drafts, submissions, permissions, unreferenced attachments, and session-owned Git worktrees, and retain hashed command receipts for idempotent retries. Parent sessions, siblings, shared directories, and worktrees referenced by surviving sessions remain intact. Filesystem cleanup is validated before removal; if it fails, the database transaction rolls back so the archived transcript remains available for retry.

After an archive commits, the server reclaims build output in the archived branch's Relay-owned repository worktrees in the background. Only directories named `target` that Git reports as wholly ignored are removed, and only in worktrees under `ROOT/.relay/sessions`. Tracked changes, untracked files, commits, branches, worktrees, transcripts, and connected directories are retained, so unarchiving still works. The cleanup is idempotent and skips missing paths; a failure is logged and leaves the files in place. It adds no persisted state.
